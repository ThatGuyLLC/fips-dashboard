What is a FIP?

From FIP-0001 and the FIPs repo.

A Filecoin Improvement Proposal is a design document for changing Filecoin: the protocol, the standards clients share, or the governance process itself. It sets out the change precisely and argues for it, and its git history becomes the permanent record of how the decision was made. A change to a single client doesn't need a FIP; anything that affects several implementations, or that they all need to agree on, does.

Author (champion)Writes the FIP, leads the discussion, builds consensus and records objections. Requests each status change with a pull request.
FIP editorsCheck a FIP is complete and sound, assign its number, merge it and process status changes. They handle the editorial side and don't judge proposals. Currently: Jennifer Wang, Alex North, Jorge Soares, James Bluett, Molly Mackinlay, Rod Vagg, Hannah Howard.
Core DevsDiscuss core FIPs in Core Devs meetings and decide which ones go into a network upgrade.
ImplementersBuild accepted FIPs into the clients and agree upgrade scope and timing on the implementers' calls.

99 FIPs are in the repo today. The rest of this page follows them through the process.

Proposing a FIP, step by step

From FIP-0001's work flow and proposing.md.
  1. Test the ideaAsk the community first, in FIP Discussions, whether the idea is new and has support. It saves writing a proposal that prior work already ruled out.
  2. Write the draftFork the FIPs repo and write the proposal from the template. Add a discussions-to link so people know where to comment (it can't be a pull request).
  3. Open a pull requestAn editor reviews the first PR, checks it's complete and well formed, assigns a number and merges it. The FIP is now a Draft.
  4. IterateRefine the Draft with follow-up PRs. Non-core FIPs need an implementation before moving on. For core FIPs, ask for a slot on a Core Devs agenda and prepare the matching change to the Filecoin spec.
  5. Last CallWhen the Draft is mature, ask for Last Call. The editor sets a review-period-end, normally 14 days out. Material changes or unresolved objections send it back to Draft.
  6. Accepted or FinalA clean Last Call makes a core FIP Accepted and any other FIP Final. Accepted core FIPs go to the implementers and into upgrade scope planning.
  7. Ship itA core FIP becomes Final once at least two clients implement it, the spec is updated and the community adopts it, which normally means its network upgrade has activated.

Each status change is a pull request from the author, reviewed by an editor. If an author steps away, they or the editors can hand the FIP to a new champion.

Types of FIP

Set in each FIP's type and category headers.
CoreTechnical87

Changes that need a consensus upgrade (a network upgrade), or that will matter for one. These are the FIPs that go through Accepted and ship in an upgrade.

NetworkingTechnical1

Changes to how data propagates or to Filecoin's network protocols.

InterfaceTechnical1

Client API and RPC standards, and conventions such as method names.

InformationalTechnical (FRC)18

Design notes, guidelines or conventions that don't propose a protocol change. Following them is optional. Kept as FRCs (Filecoin Request for Comments) in their own folder.

OrganizationalFOP2

Changes to processes around Filecoin, including governance and the FIP process itself. Usually need community consensus.

RecoveryFRP0

A one-off state change to fix something the normal protocol can't, such as a bug that destroyed value. Only allowed under tightly defined criteria.

Counts come from the FIP files' headers and the FRCs folder. 8 technical FIPs don't name a subcategory in their header. Keeping a FIP to one focused idea makes it more likely to succeed.

What goes in a FIP

FIP-0001's required sections, in order. Start from the template.
  • PreambleHeader fields: number, short title, authors, status, type, category, discussions-to, and where relevant requires, replaces or review-period-end.
  • Simple SummaryA plain-language explanation anyone can follow.
  • AbstractAbout 200 words on the technical issue.
  • Motivation (optional)Why the current protocol falls short. Optional in the template, but protocol changes without it may be rejected.
  • SpecificationDetailed enough that independent teams can build interoperable implementations.
  • RationaleWhy this design: alternatives considered, related work, and how objections were handled.
  • Backwards CompatibilityRequired whenever something breaks: what, how badly and how it's handled.
  • Test CasesRequired for consensus changes; linked where useful for others.
  • Security ConsiderationsRequired for every FIP. A FIP can't become Final until reviewers judge this section sufficient.
  • ImplementationsNeeded before Final, not before Draft: "rough consensus and running code".
  • Copyright WaiverFIPs are public domain (CC0).
